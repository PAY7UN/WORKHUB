# 解析插件目录

这里是**项目开发者发布解析插件**的地方。

插件是什么：把这台机器收到的字节变成人话的那段逻辑。
「协议类型」说的是这套字节长什么样（帧头、校验、命令码），
「解析插件类型」说的是谁来把它读懂——同一套协议可以有不止一种读法，
所以插件是可替换、可多选的，不是写死在协议里的一个字段。

## 一个插件长什么样

一个插件就是一个目录：

```
plugins/<插件目录>/
  manifest.json    清单：id、名字、发布者、版本、协议
  index.mjs        实现：导出 createParser() 与 decode(frame)
```

装上这个目录，重启服务，界面上「解析插件类型」里就能选到它。

## manifest.json

```json
{
  "id": "vendor-json-line",
  "name": "厂家 JSON 行",
  "version": "1.0.0",
  "publisher": "某某设备组",
  "summary": "一行一个 JSON 对象：把 JSON 摊成字段。",
  "entry": "index.mjs",
  "protocol": {
    "name": "厂家 JSON 行",
    "summary": "以换行结尾的 UTF-8 JSON 对象，一行一条消息。",
    "framing": { "kind": "delimiter", "delimiter": "0a" },
    "encoding": "utf8"
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `id` | 全局唯一。字母数字开头，可带 `.` `_` `-` |
| `name` | 人看的名字 |
| `publisher` | **发布者**：谁维护这套解析。界面上会显示它 |
| `version` | 版本号。界面上会显示它 |
| `summary` | 一句话说明这套解析在干什么 |
| `entry` | 入口模块（相对插件目录），默认 `index.mjs` |
| `protocol` | **可选**：插件自带一套协议 |
| `protocolId` | **可选**：挂在已有协议下（同一套协议的第二种读法） |
| `transports` | **可选**：适用于哪些接入方式，`["serial"]` / `["tcp"]` |
| `spec` | **可选**：协议详情，界面上「协议详情」那块会摊开它 |

### `transports`：这套解析在哪种口上用得上

串口与网口是两种设备：车载屏插在本机串口线上，定位终端走 TCP 连平台。
两边的协议清单**不是同一份**——写清楚了，界面才只给对的那一套。

| 值 | 意思 |
| --- | --- |
| `["serial"]` | 只在串口页出现（如通达 LED2 这类车载屏协议） |
| `["tcp"]` | 只在网口页出现（如 JT/T 808 这类终端连平台的协议） |
| `["serial", "tcp"]` | 两种口都能用 |
| 不写 | 不挑，哪儿的口都能用 |

写错了（比如 `["usb"]`）这个插件就装不上——左下角「有插件没装上」里会说明错在哪儿。
自带的协议（写了 `protocol`）会继承这个范围。

这个范围还决定插件的说明书落在哪儿：记录区的「工具」目录下分着「串口」「网口」两个子目录，
只归一边的进对应的那个目录，两种口都能用的留在「工具」根下。

### 两种绑定方式

**自带协议**（写了 `protocol`）：这套协议只有这个开发者认，
它会作为一���新的**协议类型**出现在界面上，协议类型下的默认解析插件就是它。

**挂在已有协议下**（只写 `protocolId`）：协议是别人的，解析是自己的。
同一套协议有两种读法时用这个——比如通达 LED2 有官方实现，也有厂家自己的实现。
这时协议类型是已有的那个，插件类型是可选的这一层。

`protocol` 与 `protocolId` 同时写时，以 `protocol` 为准（自带协议优先）。

## 入口模块要导出什么

```js
/**
 * 切帧器：决定一帧到哪儿为止。
 * 喂进一段字节，返回这次能确定的完整帧。
 */
export function createParser() {
  let buffer = Buffer.alloc(0);
  return {
    push(chunk) { /* ... */ },
    flush() { /* ... */ },
    pending() { /* ... */ },
  };
}

/**
 * 解一帧：读成文本与字段。
 */
export function decode(frame) {
  return {
    text: '给人看的一行字',
    hex: '帧的十六进制',
    fields: [{ key: '字段名', value: '字段值', raw: '原始字节' }],
    summary: '列表里显示的那一行',
  };
}
```

`createParser()` 返回的对象要满足三个方法：

- `push(chunk)`：喂进一段字节，返回**本次能确定的完整帧**（`Buffer[]`）。
  没凑齐就压着，下次接着凑。
- `flush()`：结束（或空闲超时）时把压着的残余吐出来。
- `pending()`：还压着多少字节。

`decode(frame)` 返回：

| 字段 | 说明 |
| --- | --- |
| `text` | 给人看的一行字（记录列表里显示的那行） |
| `hex` | 帧的十六进制（展开原始字节时显示） |
| `fields` | 解析出来的字段，界面上会一张张摊开 |
| `summary` | 概览行；不写就用 `text` |
| `parsed` | 结构化结果（可选） |

## 组包（可选）：不只能读，还能发

插件不导出 `builds` 与 `encode` 也完全能用——它就只是个「只能读不能写」的解析器。

导出了，界面上「组包下发」才有内容：人填几个参数，服务端按协议组装成字节帧发出去。

```js
/**
 * 能组哪些命令：界面照着这份清单渲染表单，不自己猜协议。
 */
export const builds = [
  {
    kind: 'platform.text',
    code: '0x8101',          // 协议里的消息 ID，摆出来人才知道发出去的是哪条
    dir: 'down',
    name: '文本信息下发',
    desc: '一句话说明这条命令干什么',
    fields: [
      { key: 'text', label: '文本内容', type: 'text', maxBytes: 1023, required: true },
      { key: 'flag', label: '标志', type: 'u8', bytes: 1, defaultValue: '0' },
    ],
  },
];

/**
 * 组一条命令：把参数组装成字节帧。
 * 参数填错要抛错——静默截断会发出去一帧「看着对、其实错」的东西。
 */
export function encode(request) {
  // request = { kind: 'platform.text', args: { text: 'hello', flag: '0' } }
  return Buffer.from([/* ... */]);
}

/**
 * 把组出来的帧按协议结构切成几段（可选）：发之前让人逐段核对。
 */
export function describeFrame(frame) {
  // 返回 [{ name: '消息 ID', hex: '00008101' }, ...]
  return [];
}
```

### 字段类型

字段的 `type` 决定人怎么填、占几个字节。`bytes` 是定长字段的宽度，
`maxBytes` 是变长字段的上限——**两者至少要写一个**，界面才校验得出来。

| 类型 | 人怎么填 | 宽度 |
| --- | --- | --- |
| `u8` / `u16` / `u32` | 十进制（`0x` 开头也认） | 1 / 2 / 4 字节 |
| `hexU8` / `hexU16` / `hexU32` | **十六进制** | 1 / 2 / 4 字节 |
| `text` | 文本，按 UTF-8 发出 | `maxBytes` |
| `hex` | 十六进制字节 | `bytes` 或 `maxBytes` |

整数字段分两族，是因为**同一个数字有两种读法**：
消息 ID 在 JT/T 808 里历来写成 `0x8101`，按十进制填 `8101` 会被当成 33025——
一个完全合法却完全不是那个意思的值。用 `hexU16` 把这件事写进类型里，
界面就按十六进制校验，不给人犯糊涂的机会。

`custom: true` 那条命令表示「协议清单里没有的消息」：
人自己给消息 ID，正文也得一行一个字段地定义（名字、类型、宽度、值），
服务端照着拼。

## 装在哪

服务按这个顺序找插件目录，谁存在用谁：

1. 环境变量 `WORKHUB_PLUGIN_DIR`
2. 当前工作目录下的 `plugins/`
3. 仓库根下的 `plugins/`（开发时）
4. 服务所在目录上一级的 `plugins/`（安装包里）

## 插件坏了怎么办

插件坏了**不会**让服务起不来，也不会影响别的插件：

- 清单写错、入口模块加载失败、该导出的函数没导出——都只记一条警告，
  警告会出现在接入页左下角「有插件没装上」里。
- 协议 id 撞了、插件 id 撞了——同样只记警告，那个插件不装。

插件必须在 Node 里跑（用到 `Buffer`），所以入口要用 `.mjs` 或 `.js`（ESM）。
