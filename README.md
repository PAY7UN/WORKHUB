# WorkHub

[![CI](https://github.com/PAY7UN/WORKHUB/actions/workflows/ci.yml/badge.svg)](https://github.com/PAY7UN/WORKHUB/actions/workflows/ci.yml)

文档与原件一体化归档平台。笔记用 Markdown 写，压缩包 / 图片 / PDF 按原样存；
文档与 Agent 配置均存储在服务端，访客浏览器不再持有模型凭据，加密文档的正文始终留在服务端。

## 技术栈

| 层 | 技术 |
| --- | --- |
| 前端 | React 19 + TypeScript + Vite + Tailwind CSS v4 + shadcn/ui |
| 后端 | Node.js + Express（开发态直跑 `.ts`，发布态编译成 `.js` 随包发布） |
| 存储 | SQLite（better-sqlite3），单文件免运维 |
| 模型 | OpenAI 兼容接口（默认 MiniMax），由服务端持有凭据 |

## 启动

```bash
npm install

# 终端 1：服务端（默认 http://localhost:8787）
npm run server

# 终端 2：前端（默认 http://localhost:8080，/api 自动代理到服务端）
npm run dev
```

也可以一条命令同时启动（`concurrently` 已在 devDependencies 中）：

```bash
npm run dev:all
```

首次启动会在 `data/workhub-v2.db` 自动建库。示例文档**仅在显式设置 `WORKHUB_SEED_DEMO=1` 时**灌入，
正式部署默认是空库（详见 `.env.example`）。

### 生产模式：一个进程就是完整应用

```bash
npm run build     # 产出 dist/
npm run server    # 同一个端口既提供 API 也提供前端页面
```

服务端会直接托管 `dist/`（`server/index.ts` 末尾的静态中间件），
所以生产环境不必再另摆一个 Caddy/nginx 托静态站点——少一个组件就少一处配置、一处证书、
一处「页面能开但接口 404」的排查点。构建产物不在时只提供 API，并在日志里提示。

## 零环境部署：目标机不用装 Node

服务器上装 WorkHub 最容易卡住的地方从来不是 WorkHub，而是「先装 Node、再 npm install、再起服务」——
每一步都是别人机器上不可控的变量（版本、镜像、编译工具链、代理、内网连不上 npm）。

所以发布包是**自带环境**的：

| 包里带什么 | 干什么 | 大概多大 |
| --- | --- | --- |
| `server/*.js` | 服务端编译产物。发布态真正被执行的就是它，不依赖目标机的 Node 能不能直跑 `.ts` | 几百 KB |
| `node_modules/` | 服务端运行时真正需要的那 70 个包。目标机不用 `npm install`，升级时也不必在生产机上装依赖 | 约 12 MB |
| `runtime/node.exe` | 一份自带 Node（版本跟打包机一致，better-sqlite3 的原生二进制一定对得上） | 约 80 MB |

包里**不带数据**：`data/`（数据库与正文）、`logs/`、`.env` 一律不进包——
升级换的是代码，不是数据。

### 打包

```bash
npm run pack:server -- --out release
```

打包顺带做四件事：重建前端（`dist/`）、编译服务端（`server/*.js`）、收集运行时依赖、准备自带 Node。

| 参数 | 作用 |
| --- | --- |
| `--out <目录>` | 产物目录，默认 `release/` |
| `--skip-build` | 不重建前端、不编译服务端（产物已经就绪时用） |
| `--no-runtime` | 不带自带 Node（目标机自己装了 Node 时用，包小 80MB） |
| `--no-deps` | 不带依赖（目标机自己 `npm install` 时用） |

产物是 `workhub-server-<版本>.zip` 和同名的 `.sha256`。
把它挂到 GitHub Release（资产名保持 `workhub-server-<版本>.zip`）就能被自动升级认到。

打完包先自己看一眼它是不是真的「自带环境」：

```bash
npm run pack:check
```

它会逐项核对：服务端是编译产物、运行时依赖在包里、自带 Node 在包里、
文件清单跟包里的东西对得上、`.sha256` 对得上。
少一样，目标机的「解压即用」就是空话——而这种缺失往往要到客户机器上才暴露。

发版有现成的工作流（`.github/workflows/release.yml`）：Release 一发布，
它会在 Windows 上打这个包、自检，再把包挂到 Release 上。

发版这一段有两道「不许少发」的闸门：

- 上传前**清点资产**（`scripts/ci/check-release-assets.mjs`）：
  这一版该有的五个文件（服务端包 + 校验值、托盘包 + 校验值、安装程序）
  少一个就当场失败，不让「少发」变成「发得挺顺」；
- 上传后**回头核对**（`scripts/ci/verify-release-assets.mjs`）：
  直接问 GitHub 这份 Release 上到底挂了哪些资产，不信流水线自己的结论。

这两道闸门是被真实事故逼出来的：v0.3.0 少挂了托盘的 `.sha256`，
打包与校验全过、流水线全绿，只有把 Release 的资产清单拉下来对一遍才发现。

### 铺到机器上：首装和升级走同一条路

```powershell
# 管理员身份的 PowerShell
npm run deploy -- -Package .\release\workhub-server-1.0.0.zip
```

`scripts/deploy.ps1` 依次做：取包（本地 zip 或 URL）→ 校验 sha256 → 解压 →
**停掉正在跑的服务** → 铺到部署目录（`data/`、`logs/`、`.env` 保留不动）→
清掉新版里已经没有的旧文件 → 注册/重启服务 → 验活。

**首装和「用包升级」是同一条命令**：升级时再跑一遍就行，代码覆盖、数据保留。
目标机因此只需要「解压 + 一条命令」：不装 Node、不跑 npm、不联网。

两个容易踩的坑，脚本已经替你处理了：

| 坑 | 会怎样 | 脚本怎么处理 |
| --- | --- | --- |
| 直接往已存在的目录里拷 | 新代码落进 `server\server`，看着部署成功了，其实在跑旧代码 | 先整个搬进暂存目录，确认拷全了再一份份换过去 |
| 覆盖正在运行的 `runtime\node.exe` | Windows 不让覆盖，铺到一半失败 | 铺文件之前先把服务停掉，等端口腾出来 |

默认部署目录是 `%ProgramData%\WorkHub\app`（`-Task` 模式下是 `%LOCALAPPDATA%\WorkHub\app`）。

| 参数 | 作用 |
| --- | --- |
| `-Package <路径或URL>` | 发布包。不填就只就地重装服务（改完配置、换了 Node 之后用） |
| `-AppDir <目录>` | 部署目录 |
| `-Port <端口>` | 服务端口（不填就读 `.env` 里的 `WORKHUB_PORT`，再不行用 8787） |
| `-Task` | 用任务计划程序代替 Windows 服务（不需要管理员权限） |
| `-Force` | 端口被占用时也继续 |
| `-NoStart` | 只铺文件，不注册服务 |
| `-DryRun` | 只打印将要执行的动作 |

### 自带运行时的替换规则

「目标机上那份自带 Node 怎么办」，三种场景三种做法：

| 场景 | 行为 | 为什么 |
| --- | --- | --- |
| `deploy.ps1` 铺带运行时的包 | 整块换掉 | 铺之前服务已经停了，这个 exe 不再被占着 |
| `deploy.ps1` 铺不带运行时的包 | 保留目标机上原来那份 | 那台机器上只有这一份 Node，删了它服务就再也起不来了 |
| 服务端自动升级 | 永远不换 | 正在跑的服务就占着它，覆盖必然失败；运行时大版本升级也该由人工安排重启窗口 |

所以**换自带 Node 运行时 = 用 `deploy.ps1` 重新铺一次包**，不是点升级。

## 部署成 Windows 服务（服务器用）

桌面端用托盘就行；服务器上要的是「开机自启、崩了能自己爬起来、没人管也在跑」，
这一节就是干这个的。

```powershell
# 管理员身份的 PowerShell
npm run service:install
```

装完是个真正的 Windows 服务（`services.msc` 里能看到）：

```powershell
sc.exe query WorkHub       # 看状态
sc.exe stop WorkHub        # 停（走优雅停机）
sc.exe start WorkHub       # 起
```

### 它到底装了什么

没有引入 nssm / winsw 这类第三方二进制。脚本用**系统自带的 .NET Framework 编译器**
（`csc.exe`，Win10/11 与 Server 2012+ 都带）现场编一个几十 KB 的小 exe 当服务宿主，
它负责：

| 活儿 | 怎么做 |
| --- | --- |
| 拉起 node | 子进程，工作目录就是代码目录，`.env` 从那儿读。**优先用目录里自带的 `runtime/node.exe`**，目标机因此不用装 Node |
| 认服务入口 | 按约定找入口：`server/index.js`（发布态编译产物）优先于 `server/index.ts`（仓库态源码）；要手工指定就在代码目录放一个 `.workhub-entry` 写上相对路径 |
| 收日志 | node 的 stdout/stderr 转到 `logs/service.log`（带时间戳和级别） |
| 崩溃自愈 | node 崩了自己拉起来，退避 5/10/15… 秒；连续 5 次拉不起来才放弃 |
| 干净停止 | 收到停止指令先调服务端的停机接口，让它把事务收完；超时才强杀 |
| 不留孤儿 | 子进程关进 Windows Job Object：宿主被强杀，node 跟着死，不占着端口 |

「崩溃自愈」放在宿主里而不是交给服务管理器，是因为外部的重启策略各有各的脾气——
任务计划程序就不会重启「被终止」的任务。放在宿主里，两种安装方式的行为才是一套的。

### 没有管理员权限时

```powershell
npm run service:install -- -Task
```

改用任务计划程序：不需要管理员权限，开机登录后自动起来，崩了也会被拉起。
但它有两个边界：用户没登录时不跑，任务计划程序自己被禁用时也不跑。
真要无人值守，还是用服务模式。

### 常用参数

```powershell
# 指定代码目录（默认仓库根）、端口、node 路径
# 不给 -Node 时优先用代码目录里的 runtime\node.exe，再从 PATH 和常见安装位置里找
npm run service:install -- -AppDir D:\WorkHub -Port 8787 -Node "C:\Program Files\nodejs\node.exe"

# 只看要做什么，不真改系统
npm run service:install -- -DryRun

# 端口被占用时强行装（服务多半起不来）
npm run service:install -- -Force
```

### 卸载

```powershell
npm run service:uninstall
```

停服务、注销注册、清掉残留进程、删安装目录；**数据库、正文、日志一律不动**。
装服务时发的那把机器令牌也会一并撤销——它能重启服务，留着等于把钥匙留在门上。

### 两个要留心的

- **服务以 LocalSystem 运行，读不到用户环境变量。** 配置请写进代码目录下的 `.env`，
  别指望设过的用户级环境变量能传进去。
- **托盘托管和服务托管别同时开。** 两个都想拉起同一个端口，谁后起来谁撞
  `EADDRINUSE`（服务端会重试 10 秒，然后放弃）。

### 改 PowerShell 脚本前先知道两条

1. **`.ps1` 必须存成「UTF-8 带 BOM」。** Windows 自带的 PowerShell 5.1 读 `.ps1` 时，
   文件开头没有 BOM 就按**系统 ANSI 代码页**解码。中文 Windows（代码页 936）上，
   UTF-8 里的中文会被拆成乱码，某些字节序列还正好落成引号或反引号——
   脚本直接**解析失败**，一行都跑不起来，报错还是 `Missing closing '}'`，
   完全指不到病根（很容易被误判成「脚本被改坏了」，其实是文件编码不对）。
   `scripts/lib/ps-encoding.test.mjs` 盯着这条，顺带用 PowerShell 自己的解析器
   把每个 `.ps1` 过一遍，语法错也一并报出来。
2. **`.env` 的解析规则只有一份实现**（`scripts/lib/env.ps1`），
   `deploy.ps1` 与 `install-service.ps1` 都从那儿取端口。
   别在脚本里另写一份——两份实现迟早分叉，而分叉之后的症状是
   「服务照常起，只是停不下来，只能强杀」。

## 托盘工具（Windows）

一个托盘图标 + 一个菜单，不做完整界面。一套代码两种模式：

| 模式 | 用途 | 行为 |
| --- | --- | --- |
| `local` | 使用者本地版 | 托盘自己拉起并守护本机的 WorkHub 服务进程（菜单可启停） |
| `remote` | 运维管理面板 | 托盘只通过 HTTP 跟远端服务器说话 |

```bash
npm run tray      # 开发态启动（Electron 自带运行时）
```

- **使用者机器上不需要另外装 Node**：托盘用 `ELECTRON_RUN_AS_NODE=1` 让自带的运行时当纯 Node 用。
- **托盘被强杀不会留下孤儿服务**：服务进程盯着父进程 PID，父进程没了就自己退出、释放端口
  （Windows 不像 Unix 会自动收拾孤儿进程）。
- 配置放在 `tray/tray.config.json`（按机器而异，不进版本库；样例见 `tray/tray.config.example.json`）：
  `mode` / `target` / `appDir` / `entry` / `token` / `hotkey` / `update`。
  配置文件按「离用户最近」找：托盘目录 → **exe 旁边** → **用户数据目录**（`%LOCALAPPDATA%\WorkHub`）。
  早期版本把配置放在 `%APPDATA%\WorkHub`，跟数据目录分在两处；那个位置仍然认，
  认到就自动搬到数据目录去——**配置和数据在一起，使用者只认一个目录**。
  把配置放在 exe 旁边、再把 `appDir` 指到同一个目录，就是一套**便携部署**：
  程序、配置、数据库、日志全在一个文件夹里，整个拷到别的机器照样跑。
  托盘自更新时这些文件在保护名单（`data` / `logs` / `.env` / `.env.bak` / `tray.config.json`）里，不会被覆盖掉。
  托盘菜单里有「打开数据目录」，直接跳到那个文件夹。
- **数据位置可以自己挑**：装完第一次运行时会有个向导问「数据放哪儿、要不要开机自启动」
  （见「[首次运行向导](#首次运行向导)」）；装好之后也能改——菜单里的「更改数据目录…」会打开系统目录选择框，
  选好之后托盘把 `.env`、数据库、vault、日志一起搬过去，记住新位置，再重启一次托盘。
  几条规矩（都是踩过才知道的）：
  - 服务在跑的时候不搬——SQLite 的库文件正被占着，搬过去的是半截文件，而且不报错。
  - 目标目录里已经有一份数据时先问一句；确认覆盖的话，原有的数据先挪成 `.replaced-…` 备份，**不直接删**。
  - **搬而不删**：旧目录里的东西留着，出了事能回头找；删旧数据是使用者的决定。
  - 「搬到哪儿了」记在**锚点**上（exe 旁边；装到 Program Files 写不了就退到 `%LOCALAPPDATA%\WorkHub`），
    不记在数据目录里——数据目录正是被改的那一方，配置跟着它走等于没记。
- **`%APPDATA%\workhub-tray` 不是数据目录**：那是 Electron（Chromium）的运行时目录，
  里面的 `ShaderCache` / `GrShaderCache` / `GPUPersistentCache` 是显卡着色器缓存，
  `Local State` 是 Chromium 的状态，`lockfile` 是单实例锁——删了会自己长回来，删的时候托盘别在跑。
  真正的数据一直在 `%LOCALAPPDATA%\WorkHub`。
  现在托盘把 Chromium 的运行时目录也收进工作目录（`<工作目录>\electron`），
  于是**所有文件只落在一个文件夹里**；升级前留下的那个 `%APPDATA%\workhub-tray` 空壳可以直接删掉。

#### 工作目录（`appDir`）管着哪些东西

`appDir` 是**工作目录**，下面这些全都跟着它走，开发态与打包态都一样：

| 东西 | 位置 | 说明 |
| --- | --- | --- |
| `.env` | `<工作目录>\.env` | 密钥、管理员初始密码、端口 |
| 数据库 | `<工作目录>\data\workhub-v2.db` | 服务端默认按代码目录定位，托盘会显式掰过来 |
| vault | `<工作目录>\data\vault` | 同上 |
| 日志 | `<工作目录>\logs\` | 服务日志、托盘日志、升级日志、升级结果摘要 |
| Chromium 运行时 | `<工作目录>\electron\` | 着色器缓存、单实例锁等（打包态才有；开发态留在 Electron 默认位置，免得污染仓库） |

掰过来这件事托盘是用环境变量（`WORKHUB_DB_V2` / `WORKHUB_VAULT_DIR` / `WORKHUB_LOG_DIR`）告诉服务端的，
环境变量优先于 `.env` 文件——所以 `.env` 里别再写这两个路径，写了也不生效（托盘会在日志里说一声）。

几个跟部署有关的细节：

- **`.env` 会被备份成 `.env.bak`**：`.env` 丢了（误删、被杀毒软件隔离、同步工具排除）时，
  托盘会拿备份恢复，**不会**重新生成密钥——新密钥解不开库里已有的文档，而且不报错。
- **`.env` 丢了、备份也没了，但数据库还在**：托盘不会重建配置，而是明确告诉你缺什么。
  确认数据可以舍弃的话，删掉数据库文件再来一次。
- **`.env` 开头带 BOM 会被自动去掉**：Node 的 `--env-file` 不认 BOM，会静默丢掉文件里的**第一个**变量
  （通常是密钥），服务端于是报「生产环境未配置密钥」——而密钥明明就在文件里。
  记事本、PowerShell 5.1 保存出来的文件都带 BOM，服务端与托盘两侧都有兜底。
- **端口**：托盘与服务端按同一套规则读（进程环境优先于 `.env`，新名 `WORKHUB_PORT` 优先、旧名 `MDHUB_PORT` 兜底），
  免得两边指向不同的端口——那种情况表现是「菜单说停了，服务明明在跑」。

### 像可执行程序一样调用

托盘不该只是「装完就躺着的图标」，它得像个能随时叫起来的程序：

| 叫法 | 怎么用 |
| --- | --- |
| 全局快捷键 | 默认 `Ctrl+Alt+W`，按一下就打开网页（不用找图标）。改配置里的 `hotkey`；写空字符串表示不要注册 |
| 命令行 | `WorkHub.exe --open` 直接打开网页 |
| 桌面快捷方式 | 目标填 `WorkHub.exe`，参数填 `--open` |
| 又点了一次图标 | 不会起第二个托盘：第二次启动只是让已有实例把网页打开 |

单实例是上面几条能成立的前提：托盘要守护本机的服务进程，
起两个就会抢端口，然后两个托盘互相打架。快捷键被别的程序抢走也不影响托盘——
注册不上就只在日志里记一笔，托盘照常干活。

### remote 模式：拿托盘当运维面板

`mode: "remote"` 时托盘不碰本机服务，只跟一台远端服务器说话。菜单里的动作：

| 菜单项 | 做什么 |
| --- | --- |
| 查看服务器状态 | 版本、运行时长、内存、数据库大小、内容条数、托管方式 |
| 查看最近日志 | 服务端最近 200 行（默认，可指定行数） |
| 重启服务器 | 先弹窗确认，再发重启请求 |
| 检查服务器更新 | 查远端有没有新版本（服务端自己比 GitHub Release） |
| 升级服务器 | 先弹窗确认，再让服务端下载并解压新包 |

凭据是**机器令牌**（`x-workhub-token` 请求头），和用户登录口令是两套东西，互不通用：

```bash
# 在服务器上发一把令牌（明文只出现这一次）
npm run manage:token -- issue "运维笔记本"

# 列出已发放的令牌
npm run manage:token -- list

# 撤销
npm run manage:token -- revoke <令牌 id>

# 清掉某个标签下从未被用过的令牌（装服务反复留下的残骸）
npm run manage:token -- cleanup "windows service"
```

加 `--json` 只输出 JSON，脚本解析用（`issue --json` 会带出 id 和明文）。

把令牌填进托盘配置，或用环境变量 `WORKHUB_MANAGE_TOKEN`：

```json
{
  "mode": "remote",
  "target": "http://192.168.1.10:8787",
  "token": "mht_xxxxxxxx"
}
```

托盘在 remote 模式下每 15 秒拉一次状态，显示在菜单标题上；连不上时菜单标题直接写「离线」，
并往 `logs/tray.log` 记一条（只在状态翻转时记，不刷屏）。

对应的服务端接口（认机器令牌，不认用户会话）：

| 接口 | 说明 |
| --- | --- |
| `GET /api/manage/status` | 状态快照 |
| `GET /api/manage/logs?tail=N` | 最近 N 行日志（默认 200） |
| `POST /api/manage/restart` | 重启服务 |
| `GET /api/manage/update` | 查有没有新版本 |
| `POST /api/manage/update` | 触发升级（服务端自己下载、解压、换代码） |

重启会先判断服务是谁拉起来的（systemd / pm2 / docker / 托盘托管 / 裸跑），
再选对应的重启方式；**被托盘托管时拒绝远端重启**——那种情况归本地托盘管，
从外面再拉一个进程会跟托盘抢端口。

### 打包成 exe

```bash
npm run pack:tray
```

产物：

| 文件 | 给谁 | 说明 |
| --- | --- | --- |
| `release/WorkHub-Setup-<版本>.exe` | 正常安装 | 安装包：**安装时可以自己选目录**（默认当前用户目录，不需要管理员权限） |
| `release/workhub-tray-<版本>.zip` | 免安装 / 分发 | 解压出来是**一个 `workhub` 文件夹**，里面的 `WorkHub.exe` 双击就跑，不写注册表，放 U 盘里也能带走 |
| `release/*.sha256` | — | 校验值，自动更新会核对它 |

免安装包同时也是**托盘自更新的原料**：发布时把它挂到 tag 上，
托盘就能自己下载、解压、换掉自己（见「[托盘自更新](#托盘自更新)」）。

两个 zip 的**顶层都只有一个目录**：解压出来是「一个文件夹」，
而不是一堆文件摊在解压目录根部——使用者面对的是「一个 WorkHub」，
双击里面的东西就能用；升级时新旧两版也不会混在同一个目录里。

安装包里装的是两样东西，**目录分工是打包版的关键**：

安装目录（**安装时可以自己选路径**，默认当前用户目录，不需要管理员权限）：

| 位置 | 内容 | 权限 |
| --- | --- | --- |
| `WorkHub.exe` | 托盘程序本体（Electron 运行时） | 只读 |
| `使用说明.txt` | 给使用者看的目录说明（装完打开安装目录第一眼就能看到它） | 只读 |
| `resources/app.asar` | 托盘代码（`main.cjs`、首次运行向导、配置逻辑） | 只读 |
| `resources/payload` | 服务端代码 + 前端产物 + 服务端运行时依赖 | 只读 |
| `resources/update/apply-update.cjs` | 自更新脚本（必须在 asar 外面，见下文） | 只读 |
| `locales/`、`*.dll`、`*.pak` | Electron 运行时文件（别删） | 只读 |

数据目录（默认 `%LOCALAPPDATA%\WorkHub`，首次运行可以换地方）：

| 位置 | 内容 | 权限 |
| --- | --- | --- |
| `%LOCALAPPDATA%\WorkHub` | `.env`、数据库、vault、日志、`tray.config.json` | 可写 |

根层只放「入口 + 一份说明」，我们自己的东西一律收进 `resources\`——
否则安装目录里会躺着一个使用者看不懂、也不敢删的 js 文件。

**运行时只有一套**：托盘本身就是 Electron，`ELECTRON_RUN_AS_NODE=1` 就是完整的 Node，
服务跑在里面，自更新的更新器也跑在里面——所以安装目录里不再附带一份 `node.exe`。
以前那份自带运行时是给更新器用的（80 MB），现在更新时把托盘旁边的运行时文件
复制一份到临时目录就够了，省下的体积直接体现在安装包和升级包上。

之所以要分开：服务端是**按代码目录**定位数据库和 vault 的（`server/storage/v2/db.ts`），
打包后代码在安装目录里，数据库要是跟着落在那儿，普通用户根本写不进去——
服务一起来就报错。所以打包态用 `WORKHUB_DB_V2` / `WORKHUB_VAULT_DIR` 把它们掰到用户目录。

### 首次运行向导

装完之后第一次启动托盘，会先弹一个小向导问两件事，**然后**才是服务起来：

| 问什么 | 默认 | 说明 |
| --- | --- | --- |
| 数据目录 | `%LOCALAPPDATA%\WorkHub` | `.env`、数据库、vault、日志都落在这儿；可以改成别的盘上的文件夹 |
| 开机自动启动 | 不勾 | 勾上就写进系统登录项（`HKCU\...\CurrentVersion\Run`），下次开机自动起托盘 |

顺序是有讲究的：`.env`、数据库、日志都得落在**最终选定**的目录里，
所以向导必须在生成 `.env` 之前跑完。

向导只出现**一次**——问过就在配置里记一笔 `setupDone`。
已经有配置文件说明是重装或升级过：数据目录是人家自己挑过的，不再打扰。

三个会被当场拒绝的数据目录（理由直接显示在对话框里）：

| 选成什么 | 为什么不让 |
| --- | --- |
| 程序目录本身或它的子目录 | 托盘自更新是整块替换程序目录的，数据放在那儿，更新时会被一起带走——库没了，文档也就没了 |
| 盘根目录（`D:\`） | 它不像「一个数据目录」，更像「随手一指」，往后清理临时文件时一个手滑就是整个盘 |
| 相对路径 | 工作目录不固定，相对路径会落到意想不到的地方 |

开机自启动后来也能改：托盘菜单里有一项「开机自动启动」的勾选框，随时开关。
菜单里显示的是**系统里的真实状态**（问注册表），不是「上次勾没勾」——
使用者自己在任务管理器里禁掉之后，菜单里的勾会跟着灭掉。

向导的逻辑放在 `tray/setup.cjs`（纯逻辑 + 一层 Electron 调用）与 `tray/wizard.cjs`（界面与 IPC）里，
判据都有单测（`tray/setup.test.cjs`）：开机自启动这种事错了不会立刻暴露——
它要等下次开机才现形。

### 首次运行的行为

打包态的完整顺序：

1. **先弹向导**：选数据目录、勾不勾开机自启动；
2. 托盘在选定的目录生成 `.env`：随机密钥 + 随机管理员密码 + 一个没被占用的端口；
3. 弹窗把**初始密码当面告诉使用者**（只显示这一次）；
4. 拉起服务进程（从安装目录的 payload 里跑），页面地址 `http://127.0.0.1:<端口>`。

打包相关的几个坑（都在 `scripts/pack-tray.mjs` 里绕掉了）：

- **payload 里的 `node_modules` 要单独一条 `extraResources`**：electron-builder 的文件过滤器
  硬编码排除「复制源根部的 node_modules」，把源目录设成 `node_modules` 本身才拷得进去。
- **托盘应用要明确排除 `node_modules`**：否则 electron-builder 会按仓库根的 `package.json`
  把前端依赖（react、codemirror…）连同原生模块拖进安装包，白多四十兆。
- **打包的中间产物放临时目录**：electron-builder 解压 electron 发行包的最后一步是目录改名，
  在 IDE 打开的仓库里做目录改名会被安全删除钩子拦掉（EPERM），打包会挂在最后一步。
  服务端包的暂存目录也一样挪到了系统临时目录——它以前建在 `release/` 里，
  Windows 上文件常被杀毒软件占着清不掉，历次打包就在发布目录里攒下一堆 `.pack-staging-*`。
  现在 `release/` 里只有能发的东西（安装包、免安装包、服务端包及其 `.sha256`）。
- **better-sqlite3 只留 `prebuilds/win32-x64.node`**：它自带 10MB 的 sqlite3 C 源码和 6 个
  别的平台的预编译二进制，运行时都用不上。
- **更新器脚本要放在 asar 外面**：托盘自更新的更新器是用纯 Node 跑的，它得读自己的脚本、
  还要在托盘退出后覆盖程序目录里的文件——asar 里的文件是虚拟的，这些事都干不了。
  所以走 `extraResources` 把它放到 `resources\update\apply-update.cjs`：
  根层留给「入口 + 说明」，我们的脚本不跟使用者的文件混在一层。
- **payload 里要自带一份 Node 运行时**：更新器不能跑在托盘目录里（它一跑起来就把那个目录
  锁住了，覆盖自己就变成了不可能），而托盘自己的 exe 也不能单独复制出去用（Electron 的 exe
  旁边还散着一堆运行时文件，少一个都起不来）。纯 `node.exe` 复制到临时目录就能跑，
  所以 payload 里得有一份——服务本身用不上，是给更新器用的。

## 局域网访问

前端 dev server 已监听 `0.0.0.0:8080`，同一局域网内的设备直接用本机 IP 访问即可：

```
http://<本机内网 IP>:8080
```

查本机内网 IP：

```bash
ipconfig            # Windows：看「IPv4 地址」
hostname -I         # Linux / macOS
```

服务端启动日志也会直接打印可用的局域网地址（`http://<内网IP>:8787` 这个端口只被本机代理访问，不需要对外暴露）。

### 首次配置：放行 Windows 防火墙

Windows 防火墙默认策略是 `BlockInbound`，且 Node.js 通常没有入站放行规则，
所以**本机用内网 IP 能打开、别的设备打不开**——这一步必须手动放行一次。

以**管理员身份**打开 PowerShell，执行：

```powershell
New-NetFirewallRule -DisplayName "WorkHub Dev 8080" -Direction Inbound -LocalPort 8080 -Protocol TCP -Action Allow -Profile Private,Domain
```

只放行 8080：浏览器始终与前端 dev server 通信，`/api` 由它在**本机**转发到服务端，
后端端口不需要对外暴露。

删除这条规则：

```powershell
Remove-NetFirewallRule -DisplayName "WorkHub Dev 8080"
```

验证端口确实在监听全部网卡（`LocalAddress` 应为 `0.0.0.0` 或 `::`，
只有 `127.0.0.1` 就说明没绑全网卡）：

```powershell
Get-NetTCPConnection -State Listen -LocalPort 8080
```

### 仍然打不开时

按这个顺序排查：

1. **设备不在同一网段**。先在访问端确认 `ipconfig`，IP 需与本机同段（如都是 `192.168.1.x`）。
2. **路由器开启了 AP / 客户端隔离**。这是最常见的第二个原因：手机连同一个 Wi-Fi 却互相打不开。
   在路由器管理页（无线设置 / WLAN / 访客网络）里找「AP 隔离」「客户端隔离」「访客网络隔离」并关闭。
3. **访客网络（Guest Wi-Fi）天然隔离**。访客网络只放行到网关，设备之间不互通，
   需要把设备切到主 Wi-Fi。
4. 本机能开、别人不能开 → 基本可以确定是防火墙；别人连别的网络能开、同网段不能开 → 是隔离问题。

### 从公网访问

路由器的端口转发需要把外部端口指向本机内网 IP 的 **8080**：

- 转发生效的前提是本机拿到**固定内网 IP**（在路由器 DHCP 里按 MAC 地址绑定），
  否则重启后内网 IP 变化，转发会指向错误地址。
- 前端 dev server 没有 HTTPS，公网访问时登录密码是明文传输的。
  长期对外暴露请用 `npm run build && npm run preview`，并在前面套一层 HTTPS 反向代理。

访问者各自登录，权限按账号角色（管理员 / 访客）生效——访客能看到全部文档，但加密文档的正文必须凭已批准的访问授权才能查看。

## 管理员密码

| 场景 | 做法 |
| --- | --- |
| 直接用初始密码 | 用户名 `admin`，密码 `admin`（**首次建库时**写入） |
| 想自己指定初始密码 | 在 `.env` 写 `WORKHUB_ADMIN_PASSWORD=...`，**首次建库时**写入 |
| 登录后想换密码 | 侧边栏头像旁的钥匙图标，需输入当前密码 |
| 已经进不去 / 忘了密码 | 见下方「忘记密码」 |

初始部署密码就是 `admin`：它必须好记，因为部署的人要立刻拿它登进去改密码。
想一上来就用自己的密码，在 `.env` 里写 `WORKHUB_ADMIN_PASSWORD` 即可（仅首次建库时生效）。

> `admin` 是公开的初始值，谁都能猜到——所以登录后的第一件事就该是改掉它。
> 服务端在管理员密码仍是初始值时会提醒一句；`NODE_ENV=production` 下则**必须**显式配置，
> 否则直接拒绝启动（对外的实例不该挂着一个人人皆知的口令）。

### 忘记密码

改密入口要求先登录，而初始密码可能早就忘了。因此提供了离线重置命令，它直接改库、不需要任何登录态：

```bash
npm run admin:password -- 我的新密码

# 或让脚本生成一个强随机密码（同样只打印一次）
npm run admin:password -- --generate
```

要点：

- 命令可在服务端运行期间执行（SQLite 处于 WAL 模式，支持并发写）
- 不依赖 `WORKHUB_SECRET` 是否配置，也不会建表或灌种子数据
- 改密后**所有已登录设备的下一次请求都会因令牌指纹过期而被要求重新登录**
- 密码规则与设置页一致：至少 8 位

### 本地自动生成的密钥

本地开发若既没写 `.env`、也没配 `WORKHUB_SECRET`，可以打开 `WORKHUB_ALLOW_LOCAL_CREDENTIALS=1`：
服务端会自己生成一把 32 字节随机密钥，存到**数据库旁边的 `.workhub-local-secret`** 里。

- **跟库放在一起**：库搬走了，密钥跟着搬。放在代码目录里的话，升级换目录反而会跟库走散；
- **每次启动都读同一把**：密钥一变，库里所有 API Key 与加密文档就再也解不开了
  （表现是「模型配置莫名其妙全空了」，而日志里什么错都不会报）；
- **文件坏了而库还在时，服务端拒绝启动**并说明原因，不会悄悄换一把新的——
  悄悄换掉的话旧密文会永久失效，使用者只会以为「文档坏了」。

想改成自己管理的密钥：在 `.env` 里写 `WORKHUB_SECRET=...`（至少 32 字符）。
但要清楚，本地已经生成过密钥之后再改它，**旧密文就解不开了**——换密钥等于换一把新锁，
要连库一起换掉才是干净的。

## 环境变量

复制 `.env.example` 为 `.env` 后按需修改（服务端启动时自动加载）：

> **关于前缀改名**：环境变量统一用 `WORKHUB_` 前缀，跟产品名对齐。
> 旧前缀 `MDHUB_` 仍然认——服务端先看新名，新名没有才看旧名；两个都配时以新名为准。
> 这么做是因为这些变量不是随手配的开关，而是运行时契约：`SECRET` 改名会让
> 已加密的文档永久无法解密，`PORT` 改名会让托盘与服务端指向不同的端口。
>
> 库文件名、Cookie、前端存储键也都换成了 `workhub` 前缀，但**旧名读得到**：
>
> - **库**：磁盘上还叫 `mdhub-v2.db` 的，启动时自动搬到 `workhub-v2.db`
>   （连 WAL 伴生文件一起搬，不会丢记录）。搬不动说明还有 WorkHub 进程占着
>   那个库——这时服务端**拒绝启动**并提示先关掉旧进程，绝不拿空库顶上
>   （宁可起不来，也不能让人以为文档没了）；
> - **Cookie**：浏览器里还揣着 `mdhub_sid` 的访客会话照样认，顺手换成新 cookie；
> - **前端存储键**：新键没有时才回退旧键，读到旧的会顺手搬到新的。
>
> 一律**只读旧、只写新**——升级一次之后，磁盘与浏览器里就只剩新名字了。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `WORKHUB_SECRET` | 无（缺失则拒绝启动） | JWT 签名、Agent Key 加密主密钥，以及**文档加密主密钥的种子**（`MASTER_KEY = sha256(WORKHUB_SECRET)`），**生产必须配置**；本地需写入 `.env` 或设置 `WORKHUB_ALLOW_LOCAL_CREDENTIALS=1`（本地自动生成一把并存在数据库旁边）。改动它会让已加密文档的密文永久无法解密 |
| `WORKHUB_ADMIN_PASSWORD` | `admin`（本地） | 管理员**初始**密码，仅首次建库时写入；已有库请用 `npm run admin:password` 或侧边栏修改，改动此变量对已有库无效。`NODE_ENV=production` 下缺失即拒绝启动 |
| `WORKHUB_PORT` | `8787` | 服务端端口。默认值来自 `shared/constants.ts` 的 `DEFAULT_API_PORT`；`.env` 里改它，托盘、部署脚本、Windows 服务宿主读的都是同一个值（宿主调停机接口时也会按新端口找服务） |
| `WORKHUB_WEB_PORT` | `8080` | 前端 dev server 端口（监听 `0.0.0.0`，供局域网访问） |
| `WORKHUB_DB_V2` | `data/workhub-v2.db` | 数据库路径（索引库）。`WORKHUB_DB` 是 v1 时代的旧变量，仅作兼容兜底；改名前的 `MDHUB_DB_V2` / `MDHUB_DB` 同样认 |
| `WORKHUB_VAULT_DIR` | `data/vault` | 仓库目录：正文文件实际存放的位置 |
| `WORKHUB_LOG_LEVEL` | `info` | 服务端日志级别：`silent` / `error` / `warn` / `info` / `debug` |
| `WORKHUB_SEED_DEMO` | 关闭 | 置 `1` 时首次建库灌入示例文档（`shared/seed.ts`）；正式部署保持关闭 |
| `WORKHUB_ALLOW_LOCAL_CREDENTIALS` | 关闭 | 置 `1` 时允许服务端在本地**自动生成一把密钥**：首次启动生成 32 字节随机密钥，存在数据库旁边的 `.workhub-local-secret`（重启不变）。它管的是密钥，不是密码——密码留空就是初始部署密码 `admin`；`NODE_ENV=production` 下无效 |
| `NODE_ENV` | 未设置 | 置 `production` 启用生产模式：强制要求显式配置密钥与管理员密码 |
| `WORKHUB_MANAGE_TOKEN` | 无 | 机器令牌：托盘 remote 模式用；优先于配置文件里的 `token`。**只发给可信机器**，它等价于运维权限 |
| `WORKHUB_UPDATE_REPO` | `PAY7UN/WORKHUB` | 自动升级用的 GitHub 仓库（`owner/repo`）：比对版本、拉取发布包 |

### `.env` 的解析规则

值可以带引号（`'...'` 或 `"..."`），带引号时 `#` 是值的一部分；
不带引号时行尾 `#` 之后是注释；同一个键写多次后写的赢；
`WORKHUB_` 优先、`MDHUB_` 兜底；**文件带 UTF-8 BOM 也能读**
（BOM 后面的第一个键照样读得到——Node 自带的 `--env-file` 恰恰认不出 BOM，
会静默丢掉第一个变量，所以服务端、托盘都自己解析，不靠 `--env-file` 兜底）。

这套规则在四个地方各有一份实现，改动必须一起改：

| 实现 | 在哪 |
| --- | --- |
| 服务端 | `server/envFile.ts` |
| 托盘 | `tray/env.cjs` |
| 部署/安装脚本 | `scripts/lib/env.ps1` |
| Windows 服务宿主 | `scripts/service/WorkHubService.cs` |

`scripts/lib/env.test.mjs`（PowerShell ↔ Node）与 `scripts/lib/env-csharp.test.mjs`
（C# ↔ Node）会拿同一批样本逐条比对，有一份对不上就报错。
因为端口读错的后果不是「某个功能不好使」，而是：服务照常起在它自己的端口上，
停机接口打不通，只能强杀——而报错永远不指向「端口读错了」。

## 日志

服务端日志统一走 `server/logger.ts`，格式固定为 `[workhub][级别] 内容`：

| 级别 | 何时打印 | 去向 |
| --- | --- | --- |
| `fatal` | 进程即将终止前的最后一条消息（未捕获异常），**不受级别开关影响** | stderr |
| `error` | 启动校验失败、落库失败等异常 | stderr |
| `warn` | 降级但不中断的情况（如用量统计失败） | stderr |
| `info` | 启动横幅、建表迁移、种子数据等常规信息 | stdout |
| `debug` | 排查用的细节 | stdout |
| `notice` | 必须让用户看到的关键信息（初始管理员密码提示），**不受级别开关影响** | stdout |

用 `WORKHUB_LOG_LEVEL` 调整：`silent` 全关、`error` 只留错误、`warn` / `info` 逐级放开、`debug` 最啰嗦。
`npm run server > out.log` 时常规输出（`info` / `debug` / `notice`）进 `out.log`，错误（`error` / `warn` / `fatal`）
仍在控制台——`>` 只重定向 stdout，想把两者收进同一个文件要补 `2>&1`。

所有未处理的异常都从同一个出口出去：Express 的全局错误处理中间件把它交给 `logger`，
客户端只收到一句「服务器内部错误」，**不会拿到堆栈**（堆栈里有本机路径与依赖版本）。

两条安全约定：

- **写入前脱敏**。所有日志入参都会过一遍密钥/令牌/密码的匹配（`Bearer` 头、JSON 里的 `apiKey`、
  `password=`、URL 里的 `user:pass@` 之类），命中的值一律替换成 `***`；数据库路径只给相对形式，
  不带本机用户名目录。上游返回的错误体同样先脱敏再发给浏览器。
  唯一的例外是 `notice`：它承担初始密码提示的逐字交付，脱敏规则可能把密码本身改写
  （一旦被当成密钥替换成 `***`），那就等于给了用户一把开不了门的钥匙。
- **初始密码提示只在建库时打印**。那几行提示（初始密码是什么、该去哪里改）会出现在
  启动日志里，它不受日志级别影响。密码本身是公开的初始值，但**转贴启动日志前
  仍请把账号信息一并过一遍**。

前端日志在 `src/lib/logger.ts`：开发期全开，生产构建只保留 `error`——
访客控制台里的内部状态变化对用户没有可操作性，只会淹没真正的报错。

## 权限模型

| 能力 | 管理员 | 访客 |
| --- | --- | --- |
| 查看/下载普通文档 | 全部 | 全部 |
| 创建/编辑/删除/移动/上传 | 允许 | 服务端 403 拒绝 |
| 加密 / 取消加密 | 允许 | 拒绝 |
| 查看加密文档正文 | 允许（服务端凭主密钥直接解密，免密） | 凭已批准的访问授权（需含 `view`） |
| 下载加密文档 | 允许 | 凭已批准的访问授权（需**显式**含 `download`） |
| 申请访问加密文档 | 不需要 | 允许（进入管理员待审批列表） |
| 审批申请 / 收回授权 / 调整授权能力 | 允许 | 拒绝（403） |
| 配置 Agent（含 API Key） | 允许 | 拒绝（403） |
| 使用 Agent 问答 | 允许 | 由管理员开关 `allowGuest` 控制 |

关键点：**「对访客隐藏」已下线**——访客与管理员拿到同一份文档清单，保密不再靠"藏起来"，
而是靠**加密**：加密文档的正文只存密文，访客必须凭已批准的访问授权才能读到，且其内容
不进入任何 Agent 的检索上下文（管理员身份也不例外）。

> 老库里原先标记为「对访客隐藏」的文档，在升级时会被**自动转成加密文档**——
> 可见性开关没了，但内容对访客依然不可读。访客提交访问申请、管理员批准后即可查看。

## 文档加密（申请制）

加密是把正文挡在**访客**之外的门槛——访客必须走申请制拿到授权，Agent 一律无权读取。

在文档右键菜单点「加密文档」之后：

- 正文以 **AES-256-GCM 密文**写入 `docs.enc_cipher`，`content` 列置空，接口返回的同样只有密文
- 每篇文档一把随机数据密钥（DEK），信封加密：DEK 被**服务端主密钥**包裹一份（`docs.enc_master_dek`）
- **服务端不签发、也不存储任何访客口令**——没有密码哈希，没有封存的密码密文，没有密码派生密钥
- 加密文档**不进入 Agent 的检索范围**，管理员身份也不例外；`/agent/polish` 对加密文档直接返回 403

**原件同样能加密，而且是真的加密**：`kind='file'` 的节点加密时，
盘上的**字节**被换成密文（不是只把索引标成加密）。
把一个 zip 标成「已加密」却让它继续以明文躺在磁盘上，
只是给用户一个「它加密了」的错觉——真出事时拖走 vault 的人照样拿得到内容。
原件的解密也在服务端完成：`/raw` 与 `/download` 在授权通过后回传明文字节。

**访客只有一条路**：提交访问申请 → 管理员批准 → 凭授权免密打开（详见下一节）。
没有「拿到密码」这个选项，也就没有「密码被拖库」这条风险。

**管理员免密查看**：服务端本就持有被主密钥包裹的那份 DEK，
所以管理员打开加密文档时由服务端直接解密并返回明文。
解密全程在服务端完成，浏览器拿到的仍是明文而非密文；该动作会记入服务端日志。

**加密文档清单**（管理后台 → 访问权限，仅管理员）：看清哪些文档以密文保存、加密了多久、
当前有几个人被放行，并可从这里批量授权或取消加密。它不再单开一个分区——
加密文档本来就是为了控制「谁能看它」，拆成两处只会让人来回找同一个答案。

解锁后的明文只留在浏览器内存里，不写回全局状态、不落 localStorage；退出该文档即需重新申请。

> ⚠️ 主密钥 `MASTER_KEY = sha256(WORKHUB_SECRET)`：**改动 `WORKHUB_SECRET` 会让既有密文永久无法解密**。

> 升级说明：本次改动会 `DROP` 掉 `docs` 表里的 `enc_wrapped_dek` / `enc_salt` /
> `enc_pwd_used_at` / `enc_pw_cipher` 四列（访问密码机制的遗留物）。
> 正文密文 `enc_cipher` 与主密钥包裹的 DEK `enc_master_dek` 都留着，
> **既有加密文档照常可读**——管理员免密查看、授权后访客打开都不受影响。

## 管理后台

管理员的活儿原本挤在侧边栏一排没有文字的小图标里：授权、加密文档、改密。
图标一多就得对着看才能认出哪个是哪件事，而且每个功能各开各的弹窗，
点开一个盖住另一个。现在合成一个入口、按功能分区，
其中「访问授权」与「加密文档」本就问的是同一件事（「谁能看这篇」），
干脆并成一个「访问权限」分区。

现在只有一个入口——侧边栏的「管理」按钮（有待审批时带角标），
进去以后是**按功能拆分的分区**：

| 分区 | 干什么 | 主要位置 |
| --- | --- | --- |
| 概览 | 现在有多少事等着处理：待审批数、有效授权数、Agent 是否配好 | 管理后台 → 概览 |
| 访问权限 | 加密文档清单（谁被放行、取消加密、批量授权）、审批访客申请、收回已给出的权限、访问审计流水 | 管理后台 → 访问权限；文档菜单「访问授权」直接定位到该篇 |
| 仓库管理 | 项目、留存规则、仓库迁移 | 管理后台 → 仓库管理 |
| AI Agent | 接口地址、模型、API Key、访客开关、检索参数 | 管理后台 → AI Agent；AI 助手面板右上角齿轮 |
| 账号安全 | 修改管理员密码（需当前密码） | 管理后台 → 账号安全 |

几个约定：

- **同一件事只在一个地方出现**。文档菜单里点「访问授权」不是另开一个弹窗，
  而是打开管理后台的访问权限分区，并**限定在这一篇文档**上（右上角有「查看全部文档」可退回）。
  AI 助手的齿轮同理，落到管理后台的 AI Agent 分区。
- **分区导航在左侧**，窄屏改成横向滚动条。每个分区名下面有一行说明，
  不用猜图标是干什么的。
- **概览里的数字可点击**，点一下直接跳到该处理的分区。
- 组件位置：`src/components/app/admin/`（`AdminConsole` 容器 + 各分区），
  打开状态与当前分区放在全局 `AppContext`——入口散在侧边栏、文档菜单、AI 助手三处，
  它们要的是同一扇门。

## 访问授权（「获取权限」式申请）

加密文档的访问只有这一条路：**申请 → 审批 → 授权**。

| | 访问授权 |
| --- | --- |
| 怎么拿到 | 你自己申请，管理员批准 |
| 粒度 | 一个人一篇文档 |
| 口子多大 | **两级**：查看（`view`）与下载（`download`）分开给 |
| 能否收回 | 能，点「收回」即刻生效 |
| 有效期 | 可设 1 / 7 / 30 天或长期 |
| 留痕 | 谁申请、何时批、批给谁、看过什么、拿走什么，都在库里 |

**「能看」不等于「能拿走」。**
授权默认只有 `view`：能打开、能读，但下载会被服务端挡下（403）。
要放行下载，管理员得显式勾上 `download`——
默认就开放下载，等于让管理员在没想过这件事的情况下把文件交了出去。
访客那边会同步收敛：授权里没有 `download` 时，下载按钮是置灰的，
并说清「本次授权仅允许查看」。这份收敛是活的——访客开着文档时每隔十几秒
探一次权限状态（切回窗口时也探一次），管理员刚放开的下载能力不必等对方
关掉重开才生效；反过来管理员收窄了能力，对方界面也会自己把按钮按回去。

批准时给错能力是常事，所以授权列表里可以直接改：
点「下载原件」那一格即刻生效（`PATCH /api/docs/:id/access-grants/:gid`）。
这比「收回再重批」好——后者会把中间那段的口子状态从流水里抹掉，
「那段时间到底能不能下载」就再也查不出来。

> 以前加密文档还有第二条路——「访问密码」：管理员把密码发过来，访客输一次长期使用。
> 那条路已经下线：密码意味着服务端要存一份口令材料（无论是哈希、封存密文，
> 还是包裹数据密钥的密码派生密钥），库一旦被拖走就是一次凭据泄露。
> 现在服务端只认会话与授权，不认任何共享口令。

**访客侧**：打开加密文档时会先拿自己的会话（`WORKHUB_sid` httpOnly cookie）去问一次
「有没有已批准的授权」——有就直接打开，没有才显示申请界面。
填个名字、说明来意即可提交；管理员批准后刷新页面就能看到正文。
申请被拒会显示「未获批准」，可重新申请。

**管理员侧**：侧边栏的「管理」按钮（或文档菜单里的「访问授权」）打开面板：

- **加密文档**：哪些文档以密文保存、加密了多久、当前有几个人被放行；
  可一次勾选多篇批量授权给同一位访客，也可就地取消加密
- **待审批**：谁想看哪篇文档、为什么、什么时候提的；批准时可顺手选有效期（长期 / 1 / 7 / 30 天）与能力
- **已授权**：当前还有效的授权；能力一格直接改，点「收回」即刻让对方下一次打开就撞墙；
  已收回的收在折叠区里备查
- **访问审计**：谁在什么时候看过、下载过、申请过、批过、收过、改过能力，全在这儿

未处理的申请数会在入口图标上显示角标，不用点开就知道有人等着。

四张表支撑这套机制：`guest_sessions`（访客身份）、`access_requests`（申请与审批结果）、
`access_grants`（授权：能力、有效期、可撤销）、`access_audit`（访问流水）。
文档被取消加密时，这篇文档上的申请与授权会一并清掉——
留着只会让管理端显示一堆已经不成立的授权。

**审计流水**（`access_audit` 表，`GET /api/access-audit`）记的是动作本身：
`提交申请` / `批准授权` / `拒绝申请` / `打开正文` / `下载原件` / `撤销授权` / `调整授权`。
权限授出去之后会被追问的从来不是「批了没有」，
而是「谁在什么时候看过、拿走过什么」——这件事只有流水答得上来。
它放在管理后台的最后一个分区：这是事后追查用的账，不是日常操作界面。

**定位深链**：链接里带上申请单号（`?access=<申请单号>`），审批人点开落回本站时，
管理后台会直接跳到「访问授权」分区并高亮那一条申请，省得自己在一堆申请里翻。

## 文档分析 Agent

1. 管理员在右下角「AI 助手」面板点击齿轮，填写接口地址（预设含 MiniMax）、模型名、API Key
2. API Key 经 AES-256-GCM 加密后存入 SQLite，不下发到任何浏览器
3. 访客问答时，服务端按访客可见文档做检索 → 拼接上下文 → 调用模型 → SSE 流式返回，并标注引用来源
4. 管理员可随时关闭「允许访客使用 Agent」，关闭后服务端直接拒绝访客提问

**检索到哪个仓库**（这条最容易踩坑，所以规则写死）：

| 情况 | 检索范围 |
| --- | --- |
| 面板里选了某个仓库 | 只检索那个仓库 |
| 问题里点名了某个仓库（「B 仓库里怎么…」） | 只检索那个仓库 |
| 都没说 | 只检索**默认仓库**（库里最早建的那个） |
| 管理员在设置里划定了范围 | 取交集，范围只能收窄不能放宽 |

面板底部能看到「当前检索范围」，问完还会回传服务端实际用到的仓库名，
两处对不上就说明落点变了。仓库名互相包含时只认更长的那个
（同时存在「项目」与「项目甲」，问的显然是后者）。

## 对话式 Agent（AI 助手）

「文档分析 Agent」是**问答**：你圈定检索范围，它答。
「对话式 Agent」是**干活**：你说清要什么，它自己决定调什么能力、要不要拆给别人做、
中间缺信息就反问你，做完给一份结论。两者共用同一份模型配置与同一套权限。

它的入口是右下角的「AI 助手」浮标：任何页面都能唤起，不用先切换到某个工作区。

### 四个角色

| 角色 | 干什么 | 能调的能力 |
| --- | --- | --- |
| 总控 | 接住你的话，判断自己干还是派出去，最后给结论 | 全部 + 可委派 |
| 网页 | 按 URL 取回网页与接口，抽成可读正文 | `web.fetch` |
| 数据 | 把表格与接口数据算清楚 | `web.fetch`、`data.analyze` |
| 文档 | 在站内文档、笔记、附件里找资料 | `doc.search`、`doc.list`、`repo.list`、`attachment.list`、`agent.ask` |

工具白名单是**边界**不是建议：网页 agent 读不到库里加密文档的正文，文档 agent 发不出网络请求。

### 循环长什么样

```
想 → 做一个动作 → 看结果 → 再想 → …… → 收工
```

动作只有四种：`tool`（调能力）、`delegate`（派给别人）、`ask`（反问你）、`answer`（给结论）。
一次只做一个动作——多动作的模型看起来利索，实际上出错时定位不到是哪一步错了。

模型用「正文 + 一个 JSON 代码块」当协议，而不是官方的 `tool_calls`：
上游是各家 OpenAI 兼容网关，对 `tools` 的支持参差不齐；而正文还有额外好处——
它就是给人看的进展说明，白捡。

### 两份新能力

| 能力 | 做什么 |
| --- | --- |
| `web.fetch` | 给 URL，拿到能读的内容：HTML 抽正文（去脚本、样式、导航），JSON 解析成结构化数据。只放行 http/https，单次最多读 2 MB |
| `data.analyze` | 给表格或接口数据，算清楚：每列画像、按列分组汇总、按条件筛选、排序取前 N。**程序算数，模型只负责解读** |

两者能串起来：取回的 JSON 直接喂给 `data.analyze`，不用把数据在对话里倒来倒去。

### 数字为什么不让模型自己算

模型心算平均值会错，会把两行数据数成三行。所以 `data.analyze` 负责出数字，
模型只负责把数字说成人话。列名写错时它会直接报错并列出可用的列名，而不是给一张空表。

## 上传文件：笔记与原件

站里只有两种东西，**分清楚比什么都重要**：

| 上传的东西 | 变成什么 | 打开时看到 |
| --- | --- | --- |
| `.md` / `.markdown` | 一篇**笔记**（`kind='note'`） | Markdown 编辑器 + 分屏预览 |
| 其它格式（docx、pdf、图片、源码、**压缩包**……） | 一个**原件**（`kind='file'`），字节原样落盘 | 原件本身 |

**文件不需要配一份同名备注。**
以前上传一个 zip 会凭空多出一篇同名的 Markdown 备注——那份备注没人写，
只是系统硬凑出来的，于是「上传了但打不开、打开了是空的」成了常态。
现在文件就是文件：点开一个 zip，看到的是这个 zip 本身，
不配备注，也没有一个同名同格式的空编辑器在等着。

原件按格式分档预览：

| 格式 | 预览方式 |
| --- | --- |
| 图片（png / jpg / gif / webp / svg……） | 直接内联显示 |
| PDF | 内嵌阅读器 |
| 文本（txt / md / json / yaml / 源码……） | 取原始字节按 UTF-8 解出来原样显示 |
| 其它（zip / docx / exe……） | 一张说清「这是什么、多大、怎么拿走」的卡片 |

内联预览走 `GET /api/docs/:id/raw`（`inline` + 私有缓存），
下载走 `GET /api/docs/:id/download`：**原样回传原始字节与原始 MIME，
文件名保留原名**。笔记的下载则导出为 `.md` 文本——加密笔记导出的是**明文**，
不是密文，也不是一个看着成功、打开却是空的 .md。

加密文档这两条路都要过权限：查看要有 `view`，下载要**显式**有 `download`。
「能看」不等于「能拿走」，详见下面的访问授权一节。

前端取字节时一律带上令牌再渲染（图片、PDF 走对象 URL），不写成
`<img src="/api/docs/:id/raw">`——浏览器发那种请求不会带 `Authorization` 头，
服务端只认得 cookie 里的访客身份，管理员打开自己加密的图片只会看到一张裂图。

**压缩包不会被解开**：上传 `a.zip` 就是把这个包原样存进来。
解包会擅自改变资料的组织方式，归档的边界该由用户自己定——
要拆开的话，在本地拆好再逐个上传。

上传、删除之后仓库的文件数会立刻跟着变，不用手动刷新页面。

## 文档存在哪：仓库目录里的文件

v2 起文档正文是**真的文件**：放在 `data/vault/<仓库 slug>/docs/` 下的 `.md`，
数据库（`data/workhub-v2.db`）只留索引——路径、哈希、大小。
这决定了两件事：

- 把项目传到 GitHub，**只会带走代码**，带不走任何文档内容（`data/` 被 `.gitignore` 忽略）
- 想让文档进 GitHub，要先从仓库目录导出一份带 front matter 的 md 树

```bash
npm run docs:list      # 列出库里的文档：路径、正文大小
npm run docs:export    # 导出成 content/ 下的 md 文件树（含 manifest.json 记录 id 对应关系）
```

导出规则：目录结构照搬仓库目录（`content/<仓库 slug>/<文档路径>`），文件名前是 YAML
front matter（`id` / `name` / `tags` / 时间戳），正文原样保留。
加密文档导不出明文（库里只有密文），会被列在「已跳过」里——不会给你一个看着成功、
内容其实空着的文件。`content/` 默认在 `.gitignore` 里——
**提交它等于公开这些文档**，确认要上传再删掉那行。

## 自动升级

服务端能自己把自己换成新版本：查版本 → 下载校验 → 换代码 → 拉起来 → 验活，
任何一步不行就退回升级前的代码。

### 两扇门

| 入口 | 凭据 | 用途 |
| --- | --- | --- |
| `/api/admin/update` | 管理员会话 | 管理后台里点升级 |
| `/api/manage/update` | 机器令牌（`x-workhub-token`） | 托盘 remote 模式、监控脚本 |

两套凭据互不通用，所以升级这件事开了两扇门。

### 流程

1. **查版本**：默认去 GitHub 的 `PAY7UN/WORKHUB` 比对 Release；
   也可以用 `WORKHUB_UPDATE_MANIFEST`（自定义清单）或 `WORKHUB_UPDATE_URL`（直链）。
   查不到不算失败——没网、限流、压根没发 Release 都会发生，
   所以「没有新版本」和「查不到」在结果里是两种说法，界面上该说的话不一样。
2. **下载校验解包**：包里有文件清单与每个文件的 sha256，对不上就到此为止。
   这一步**不动正在跑的代码**。
3. **起更新器**：独立进程 `scripts/upgrade-apply.mjs`，只依赖 Node 内置模块——
   它自己就站在被替换的代码目录边上，万一新代码有 bug，
   靠的是新代码之外的自己把它救回来。
4. **预检**：新代码先在隔离目录里被拉起来试跑一次（详见下一节）。
   预检不过就到此为止，**代码一秒都不换，服务一秒都不停**。
5. **服务退出**：Windows 上运行中的代码换不掉（node.exe 被占着，
   better-sqlite3 的 `.node` 被 mmap 锁着）。更新器会等进程真的退出（最多 60 秒）。
6. **换代码**：备份 → 覆盖 → 删掉新版里已经没有的旧文件 → 依赖变了就装依赖
   （只有 `dependencies` 变了才装，`devDependencies` 不进生产包）。
7. **拉起来并验活**：撤掉升级标记让宿主把服务拉起来，然后打 `/api/healthz`；
   不通就回滚，再拉一次。

`data/`、`.env`、`node_modules` 都不在被替换范围内——**代码进包，数据不进包**。

自带运行时（`runtime/`）也不在替换范围内：正在跑的服务就占着那个 exe，覆盖必然失败。
想换运行时用 `deploy.ps1` 重新铺一次包（见「[自带运行时的替换规则](#自带运行时的替换规则)」）。

### 升级前先预检

换代码之前，新版本会先在**隔离目录**里被拉起来试跑一次：

1. 解包到临时目录，用**临时库**和**随机端口**起一个实例
   （不碰生产库、不占生产端口，起来就掐掉）；
2. 打健康检查，通了才算这一版能起来；
3. 起不来就**当场放弃**：代码没换，服务照跑。

预检实例带 `WORKHUB_PREFLIGHT=1` 标记——这个标记让「只在正式运行时才犯的错」
（比如依赖真实配置、真实数据才会炸的初始化逻辑）在预检里先暴露出来，
而不用等真的把生产代码换掉才发现。

### 起来 ≠ 稳定

健康检查通过只说明「它起来了」。有些版本起来几秒就挂——
所以健康检查通过之后还要**观察一段稳定期**（默认 15 秒，
`WORKHUB_UPGRADE_STABILIZE_MS` 可调），期间进程退出就算升级失败。

### 失败回滚

| 失败点 | 后果 |
| --- | --- |
| 下载或校验不过 | 没动过任何代码，服务照跑 |
| 预检起不来 | 没动过任何代码，服务照跑（更新器负责把服务叫醒） |
| 依赖装不上 | 回滚到升级前的代码，再拉起来 |
| 升级后健康检查不过（等 90 秒） | 回滚到升级前的代码，再拉起来；连回滚后也起不来才需要人工介入 |
| 起来了但稳定期内退出 | 同上——健康检查过了不算数 |

升级结果记在库里，界面能直接看到「成功 / 已回滚 / 需要人工看看」。

### 托盘自更新

服务端能自己把自己换成新版本，托盘也能——用的是同一套原料：**发布时打好的那个 tag 压缩包**。

| | 服务端 | 托盘 |
| --- | --- | --- |
| 包名 | `workhub-server-<版本>.zip` | `workhub-tray-<版本>.zip` |
| 谁动手换 | 服务进程自己换代码 | 独立进程换整个程序目录 |
| 入口 | 网页上的「升级」 | 托盘菜单「检查更新」 |

包名是硬约定：更新器按名字找包，名字对不上就等于没发，
而且使用者那边看不出任何异常——界面只会说「没有新版本」。
所以发 Release 时两个包都要挂上（`npm run pack:tray` 会打出托盘那个）。

托盘这边比服务端多两桩麻烦事：

1. **Windows 上运行中的程序换不掉**：托盘得先退出，
   换文件的活儿交给独立进程 `tray/apply-update.cjs`（只用 Node 内置模块）。
   更新器用的运行时是**托盘自己的 Electron**：更新时把 exe 旁边的运行时文件
   （ICU 数据、V8 快照这些）复制一份到临时目录，用 `ELECTRON_RUN_AS_NODE=1` 跑它。
   必须待在托盘目录之外——一跑起来就把要替换的目录锁住了。
   更新器等托盘退出（最多 60 秒）→ 备份 → 覆盖 → 删掉新版里没有的旧文件 → 把托盘拉起来。
2. **本地服务也得先停**：服务进程占着 payload 里的文件（better-sqlite3 的 `.node` 被 mmap 锁着），
   不停就换不掉。更新完新托盘再把服务拉起来。

所以升级期间托盘图标会消失几十秒——这是 Windows 上换程序目录的固有代价。
中途出错会自动回滚到旧版本，并把托盘拉起来；托盘本身始终不受影响。

内网部署走不通 GitHub 时，在托盘配置里指定更新源：

```json
{
  "update": {
    "manifest": "https://内网地址/manifest.json"
  }
}
```

清单格式跟服务端那份一样：`{ "version": "0.2.0", "url": "...", "sha256": "..." }`。

### 打升级包

见「[零环境部署](#零环境部署目标机不用装-node)」一节：包里除了代码，
还带着运行时依赖与自带 Node，目标机解压即用。

### 验证升级链路

```bash
npm run verify:upgrade
```

在临时目录里完整跑一遍：打包 → 预检 → 换代码 → 拉起来 → 验活 → 稳定期观察，
外加两个坏包：

| 坏在哪 | 该看到什么 |
| --- | --- |
| 起来就挂（健康检查之前就退出） | 自动回滚，版本退回上一个可用版本 |
| 连预检都过不了（语法就是坏的） | 预检当场拦下：代码没换、服务没停，结果记为失败 |

它只能在 Windows 上跑得起来（更新器要 taskkill 杀进程树、要 PowerShell 解压），
所以 CI 里单开了一个 `windows-latest` 的任务。

```bash
npm run build:server  # 编译服务端（发布态入口 server/index.js）
npm run verify   # 端到端自检
npm run verify:upgrade  # 升级链路自检（含坏包自动回滚、预检拦截）
npm run pack:check  # 查发布包是不是真的自带环境
```

这几步已经接进 CI（`.github/workflows/ci.yml`）：每次推送与 PR 自动跑
类型检查 → lint → 单测 → 编译服务端 → 端到端自检；
升级链路自检单开一个 `windows-latest` 的任务（它要 taskkill 杀进程树、
要 PowerShell 解压，Linux 上跑不了，硬凑只会验出一套假环境），
同一个任务里还会打一次发布包并自检——打包坏了不能等到发版那天才发现。
CI 里的示例库是现场生成的
（只导入 `server/db.ts` 即建库、灌示例文档、写出仓库目录），
不碰仓库里的任何真实数据——`data/` 本来就不该被提交。

`npm run verify` 会在**临时目录复制一份数据库和一份仓库目录**、用独立端口拉起一个服务端实例，
跑完 77 项检查后自动退出：服务启动、访客与管理员清单一致、错误密码 401、登录与鉴权、
Agent 配置脱敏、改密后旧令牌立即失效，文档加密全流程
（密文入库、访客拿不到正文、加密接口不再签发密码、密码相关接口均已下线、管理员免密查看），
访问授权全流程（访客取会话、无授权 403、提交申请、重复申请 409、访客读不到申请列表、
访客不能自行批准、审批前 reason=pending、批准即免密打开、授权名单可列、收回后立刻打不开），
原件与下载（上传 zip 只得到一个文件节点、不配同名 `.md` 备注、按原字节下载、
保留原文件名与原始 MIME、内联预览字节一致），
能力分级（无授权下载 403、只给「查看」时能看不能下载、在线 `PATCH` 加上 `download` 后才拿得到、
访问审计留下 `adjust` 与 `download` 记录、访客读不到审计），
以及仓库与上传（压缩包按原件存为附件、不拆成多篇文档、仓库文件数随增删同步、解包接口已下线）。

它不碰正在运行的实例，也不修改生产库与生产仓库目录——库和目录都只在副本上操作，
改密码那一步同样只在副本上执行。

> 前置条件：先跑过一次 `npm run server` 建好 `data/workhub-v2.db` 与 `data/vault/`
> （示例文档需 `WORKHUB_SEED_DEMO=1`），脚本会复制这两份做隔离验证；
> 没有库时它会直接告诉你缺什么，而不是抛一堆无关错误。

## 常用接口

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| `GET` | `/api/healthz` | 公开（健康探针：只答「能不能用」，库不可用回 503；不泄露版本与路径） |
| `POST` | `/api/auth/login` | 公开（密码登录；连续失败会触发递增退避，超限返回 429） |
| `GET` | `/api/auth/me` | 所有人（当前身份；带了令牌但服务端不认时 `tokenInvalid=true`，用来区分「本来就没登录」与「登录被作废」） |
| `POST` | `/api/auth/change-password` | 管理员（需校验当前密码，改密后旧令牌全部失效） |
| `GET` | `/api/docs` | 所有人（访客与管理员拿到同一份清单） |
| `GET` | `/api/docs/search?q=` | 所有人（标题与正文全文搜索；加密文档在库里只有密文，搜不到内容——这条边界由存储方式自动成立） |
| `POST` `PATCH` `DELETE` | `/api/docs/:id` | 管理员 |
| `POST` | `/api/docs/upload` | 管理员（上传原件：请求体是文件字节，文件名与 MIME 走 query；只得到一个文件节点，不配同名备注） |
| `POST` | `/api/docs/import` | 管理员（覆盖式导入浏览器里的历史文档：**先校验后替换**，载荷不合格原样退回，一个字节都不碰） |
| `GET` | `/api/docs/:id/download` | 所有人（原件按原字节 + 原 MIME + 原文件名回传；笔记导出为 `.md`；加密文档需授权且须含 `download` 能力） |
| `GET` | `/api/docs/:id/raw` | 所有人（内联预览原件，`inline` + 私有缓存；加密文档需授权且须含 `view` 能力） |
| `POST` `GET` | `/api/docs/:id/attachments` | 上传=管理员，列表=所有人（上传的请求体是**原始二进制**而非 multipart：文件格式千差万别，「一个文件一段字节」才是统一的） |
| `GET` | `/api/attachments/:id/download` | 所有人（按原始文件名回传，浏览器据此决定怎么打开） |
| `PATCH` | `/api/attachments/:id` | 管理员（附件改名） |
| `POST` | `/api/attachments/:id/move` | 管理员（换一篇文档挂着；只改宿主指针，不搬字节——内容寻址下同一份内容在磁盘上只有一份） |
| `DELETE` | `/api/attachments/:id` | 管理员（删附件） |
| `GET` `POST` | `/api/repos` | 读=所有人，写=管理员（仓库清单 / 新建；仓库只是资料的组织方式，不是保密边界，同名返回 409） |
| `PATCH` `DELETE` | `/api/repos/:id` | 管理员（改仓库 / 删仓库） |
| `POST` | `/api/repos/:id/docs` | 管理员（往仓库里导文档） |
| `POST` | `/api/docs/:id/encrypt` | 管理员（首次加密，不签发任何密码） |

| `POST` | `/api/docs/:id/reveal` | 管理员（免密查看加密文档正文；解密全程在服务端完成，密文不下发到浏览器） |
| `GET` `POST` | `/api/auth/guest` | 所有人（访客会话：取回 / 修改昵称，凭证在 httpOnly cookie 里） |

### 运维接口（机器令牌）

这一组不认用户会话，只认 `x-workhub-token` 请求头里的机器令牌——给没有浏览器的场景用
（托盘 remote 模式、监控脚本）。令牌在服务器上用 `npm run manage:token -- issue "<用途>"` 发放。

| 接口 | 说明 |
| --- | --- |
| `GET` | `/api/manage/status` | 状态快照：版本、运行时长、内存、数据库、各类条数、托管方式 |
| `GET` | `/api/manage/logs?tail=N` | 最近 N 行日志（默认 200，内存里最多留 500 行） |
| `POST` | `/api/manage/restart` | 重启服务（按托管方式选择 systemd / pm2 / docker / 自拉起） |
| `POST` | `/api/manage/shutdown` | 停掉当前进程（不拉新的）。被托盘托管时拒绝——托盘会把它拉回来 |
| `GET` | `/api/manage/update` | 查更新（能区分「没有新版本」和「查不到」，这两种在界面上该说的话不一样） |
| `POST` | `/api/manage/update` | 执行升级（服务退出后由独立进程替换代码；校验不过或替换失败会自动回滚） |
